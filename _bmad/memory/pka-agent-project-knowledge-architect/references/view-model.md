# 结构—运行—机制视图

业务、产品和技术三个架构维度都使用同一组三视图：

| 视图 | 文件 | 回答的问题 | 主要内容 |
|---|---|---|---|
| 结构 | `structure.md` | 由什么组成，各部分如何关联？ | 主体、对象、能力、模块、层级、边界、依赖和关系 |
| 运行 | `runtime.md` | 如何触发、流转、变化并产生结果？ | 事件、参与者、活动、状态转换、异常路径和生命周期 |
| 机制 | `mechanism.md` | 为什么这样设计，结构如何支撑运行？ | 目标、规则、约束、决策、结构支撑、运行条件、结果和验证 |

机制不是独立的规则清单。每条机制都必须指向 `structure.md` 中的具体承载者和 `runtime.md` 中的具体行为，说明它们如何共同产生预期结果以及如何验证。

## 目录契约

```text
project-knowledge/
├── business/{structure,runtime,mechanism}.md
├── product/{structure,runtime,mechanism}.md
└── technology/{structure,runtime,mechanism}.md
```

“空间—时间—逻辑”仍是理论来源；对用户呈现和新生成文件统一使用“结构—运行—机制”。

## 旧项目兼容

旧文件按以下关系读取：

- `space.md` → 结构视图
- `time.md` → 运行视图
- `logic.md` → 机制视图

发现只有旧三文件的项目时，继续把它们作为有效知识读取，不以“缺少新文件”报告错误，也不自动重命名。只有用户明确要求迁移项目知识时，才把三个目录中的旧文件成组迁移为新名称，并同步修正知识文件内部链接和 `traceability.md`；迁移不得触碰原始需求、方案、代码或交付物。

若新旧文件并存，优先读取新文件并报告重复或冲突，未经确认不得合并或删除任一版本。
