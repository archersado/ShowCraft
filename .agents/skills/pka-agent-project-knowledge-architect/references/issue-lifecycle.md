# 问题生命周期

问题不是一句待回答的话，而是推动项目知识模型演化的工作单元。每个问题用一个 `Q-ID` 从提出贯穿到验证，讨论过程写入问题记录，只有已确认且可验证的结论才进入业务、产品和技术架构。

## 最小存储结构

```text
project-knowledge/
└── issues/
    ├── index.md
    └── Q-YYYYMMDD-NNN.md
```

`issues/index.md` 只维护 `Q-ID`、标题、当前阶段、优先级、更新时间和链接。每个问题只使用一个 Markdown 文件；仅当证据附件大到影响阅读时才拆分。

## 生命周期

`captured → defined → decomposed → mapped → discussing → decided → applied → verified → closed`

可选状态：

- `pending`：缺少证据或用户决定。
- `rejected`：问题不成立或明确决定不处理，并保留理由。
- `reopened`：验证失败或外部条件改变。

阶段可以回退。不得通过跳过定义、决策或验证来伪造进度。

## 分析方法

问题定义遵循 `问题 = 期望状态 - 当前状态`。先向上追溯它服务的目标，再确定边界和成功判据；不要把症状直接当成根因。

问题分解同时使用两种视角：

- 静态分解：目标、子目标、要素、变量、模块及其关系，尽量相互独立且覆盖关键范围。
- 动态分析：触发事件、参与者、活动、状态转换、异常路径和结果，区分相关性与因果性。

关联识别将问题映射到业务、产品、技术各自的 `space`、`time`、`logic` 节点，并检查项目内已关闭问题、复盘模式候选和已登记跨项目主题。模式只能作为假设或候选方案来源；条件不一致时不得直接套用。

结构化问题通过目标、评价标准、备选方案、多维比较、选择理由和验证计划形成方案。探索性问题使用“假设—最小验证—修正”的循环，但仍要记录判断依据和停止条件。

## 四个门禁

1. **定义门禁**：期望、现状、差距、边界和成功判据足够明确，才进入分解。
2. **决策门禁**：证据、备选方案、评价标准、选择与否决理由齐备，才形成架构更新清单。
3. **更新门禁**：用户确认结论或证据足以收敛后，才更新受影响架构；讨论中的假设不得覆盖现行模型。
4. **关闭门禁**：验证成功，且结构—运行—机制与业务—产品—技术映射没有未说明的断裂，才可 `closed`。

## 架构与知识回流

`traceability.md` 只保存 `Q-ID → 目标/差距 → 方案 → 架构节点 → 验证证据` 的架构投影，不复制完整讨论。

架构更新必须满足：

- `structure` 中存在承载方案的模块或关系。
- `runtime` 中存在方案要求的运行行为或状态变化。
- `mechanism` 同时引用相关结构模块和运行行为，并说明结果与验证方式。
- 跨维度影响在 `traceability.md` 闭环，无法闭环的部分显式标记。

问题通过关闭门禁后，才可在项目复盘中提炼模式候选；至少两个项目提供独立证据后，模式才可晋升为跨项目主题。
