# 问题驱动的架构演化

把用户提出的问题变成一个有编号、有状态、可验证的问题生命周期，并把已确认的新认知落到项目知识模型。消费者是后续规划、实施、检查和复盘的人或 Agent；他们应能知道问题如何被定义、讨论和解决，改变了什么，以及还有什么没有得到回答。

执行时先完整读取 [问题生命周期](issue-lifecycle.md)。在 `project-knowledge/issues/` 为新问题分配 `Q-YYYYMMDD-NNN`，更新 `index.md`，并使用同一个问题文件贯穿 `captured → defined → decomposed → mapped → discussing → decided → applied → verified → closed`。已有 `Q-ID` 时继续原记录，不重复创建。

先用“期望状态－当前状态＝核心差距”界定问题，再进行结构分解和运行过程分析。随后识别它影响的业务、产品、技术维度及各自的结构、运行、机制节点，并匹配项目内已关闭问题、复盘模式候选和已登记跨项目主题。模式匹配只生成待验证假设，不能代替当前项目证据。

以当前项目知识和只读原始证据为边界，通过最少但能改变结论的问题，与用户澄清目标、前提、约束、方案、反例和验证方式。每轮在问题文件的 `Discussion` 中追加观点、证据、冲突、暂定结论和未解项，并明确区分事实、用户确认的决策、`inferred` 解释和 `pending` 问题；不用连续提问代替判断。

遵守定义、决策、更新、关闭四个门禁。讨论尚未收敛时只更新问题记录，不改写已确立的架构结论；`traceability.md` 只在形成架构影响时登记 `Q-ID` 的简要投影，不复制讨论全文。用户确认结论或证据足以收敛后，记录评价标准、备选方案、选择与否决理由和验证计划，先给出最小变更清单，再按 [结构—运行—机制视图](view-model.md) 仅更新受影响的 `business/`、`product/`、`technology/` 视图以及 `traceability.md`；新证据同步登记到 `sources.md`。

更新后执行关闭检查：确认机制同时指向支撑它的结构模块和符合它的运行行为，跨维度影响已经闭环或明确标记断裂，并用成功判据验证核心差距是否缩小。验证失败时转为 `reopened`，不得标记完成。问题通过关闭门禁后，才可交给项目复盘提炼模式候选。

所有写入仅发生在 `{output_folder}/project-knowledge/`；原始需求、方案、代码和交付物永远只读。
