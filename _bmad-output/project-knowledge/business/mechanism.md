# 业务架构：机制

## M-B01：以结构化版本清单降低内容生产偏差

- 目标：让每个视频有可追溯的功能来源，降低口播、演示与版本事实不一致的风险。
- 结构承载：版本特性清单、ShowCraft、任务产物（见 `structure.md`）。
- 运行行为：任务开始前校验清单；通过后将生成的脚本、动作和渲染清单保存到单次任务目录（见 `runtime.md`）。
- 结果：运营人员能依据中间产物审查内容，而不是只能审查最终视频。
- 验证：demo 任务应输出通过 schema 校验的产物；非法输入应有字段级错误。[S-001]

## M-B02：人机边界保护产品与品牌风险

- 目标：自动化提高产能，但不越过登录、发布和品牌审核的责任边界。
- 结构承载：外部产品环境、适配器边界、运营审核角色。
- 运行行为：首发环境在本地全自动执行；生成的视频在分发前必须经运营团队人工审核，发布仍处于外部流程。
- 验证：本地 run 可端到端完成；存在 `pending_review` 产物与人工审核结果；代码与文档中不包含产品凭据。[S-001, S-003]

## M-B03：内容规模随特性数量伸缩

- 目标：避免固定时长使特性较少时拖沓、特性较多时遗漏。
- 结构承载：版本特性清单、ScenePlan、Render Manifest。
- 运行行为：每个特性至少形成一个可讲解镜头；渲染层从特性数量计算时长和镜头节奏。
- 验证：同一模板分别输入 1、3、6 个特性时，镜头数和总时长随之变化；基础时长为开场/结尾 10–15 秒与每项特性 12–20 秒，超过 90 秒时拆分系列。[S-004]

## M-B04：首个发布说明作为真实验收样本

- 目标：以真实的产品语言而非模拟数据验证内容生成和演示链路。
- 结构承载：StartUpOS 桌面版、`v0.3.3` Changelog、ShowCraft run。
- 运行行为：将感知/IM、企业微信、Agent 协作和验证四组变更解析为视频镜头；不足以演示的验证条目必须标为旁白或跳过，不能捏造界面。
- 验证：一次 run 产生对每个输入组的镜头映射，且每一项都可回链源文档。[S-005]
