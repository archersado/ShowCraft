# 原始问题

如何通过渐进式提问补充 ShowCraft 的架构骨架，使产品定位、自动化边界和首个可验证交付足够清晰？

# 问题定义

- 期望状态：业务、产品和技术架构能支持一个明确的首发用例，并将真实产品自动化、审核和渲染接入的关键边界定义清楚。
- 当前状态：已确定“版本特性到介绍视频”的通用流水线，但目标客户、输入来源、产品操作授权、人工审核与视频交付标准仍为 `pending`。
- 核心差距：缺少足以选择首发工作流和风险控制模型的用户确认。
- 影响与边界：只更新 `_bmad-output/project-knowledge/`；不改变已批准的骨架计划或源代码。
- 成功判据：用户确认首发场景、自动化责任边界、审核责任和视频交付形态；架构文档能把这些决定映射到结构、运行和机制。

# 问题分解

## 静态结构

- 用户与目标受众
- 版本信息来源
- 产品演示环境与授权主体
- 审核与发布责任人
- 视频模板、品牌资产与输出渠道

## 动态过程

`触发版本发布 → 提供事实输入 → 生成/执行演示 → 审核 → 渲染/分发 → 反馈改进`

## 因果与假设

- `inferred`：首发应优先聚焦一个受控产品与单一视频类型，降低自动化和内容质量风险。
- `pending`：用户是否接受“AI 先生成计划、人工批准后才执行真实产品操作”的控制点。

## 优先级

高：这些选择决定首个 MVP 的产品边界与技术适配器优先级。

# 关联识别

## 架构视图节点

- 业务：`business/structure.md` 的运营角色与价值链；`business/runtime.md` 的审核/发布阶段。
- 产品：`product/structure.md` 的 Release Intake、Demo Orchestrator、Capture Provider；`product/runtime.md` 的任务状态。
- 技术：`technology/structure.md` 的 adapters 与外部边界；`technology/runtime.md` 的安全执行约束。

## 已有问题、复盘与跨项目主题

无。项目尚无已关闭问题、复盘或跨项目主题。

# Discussion

## Round 1

- 观点：应先提问那些会改变 MVP 范围和安全机制的选择，而非先讨论具体模型、动画和存储实现。
- 证据：S-001 的待验证断裂集中于真实产品环境、HyperFrames 契约、品牌/渠道和审核发布流程。
- 反例或冲突：若 ShowCraft 仅作为离线视频模板工具，浏览器自动化与录屏授权可移出 MVP；若必须无人值守发布，则审核与凭据隔离必须前置。
- 暂定结论：以四个高信息量问题开始澄清。
- 未解项：目标用户、输入源、自动化授权、审核与输出标准。

## Round 2

- 观点：首发场景可以收敛为“运营团队从 Changelog 同步版本事实，在本地自动生成中文功能介绍视频并人工审核”。
- 证据：用户确认运营团队面向用户做功能介绍和推广；输入来自 GitHub/本地 Changelog；本地全自动；时长按 feature 数量；中文 AI 配音/字幕；需要人工审核。[S-003]
- 反例或冲突：本地全自动不等于可在任意产品环境运行；仍需要可重复启动方式、稳定元素和测试数据。
- 暂定结论：把 Changelog Sync、Audio & Subtitle Provider、Review Gate 设为首发架构模块；审核是交付门禁。
- 未解项：Changelog 格式、产品启动/认证、时长公式、配音供应商、审核标准。

## Round 3 — 架构一致性检查

- 观点：已确认决策在三维架构中形成了可追溯闭环。
- 证据：Changelog Sync、Audio & Subtitle Provider、Review Gate 均出现在产品结构；`pending_review`、`approved`、`changes_requested` 出现在产品运行；对应的人机边界、内容伸缩和审核门禁出现在业务/产品/技术机制；`traceability.md` 已连到技术承载。
- 反例或冲突：`Local Runner` 目前以 CLI 和技术运行约束表达，尚未有独立的实现模块；是否拆分为单独服务取决于后续并发/队列需求。
- 暂定结论：不为骨架引入队列或服务；保留 CLI 作为本地 runner，待真实执行场景验证后再决定。
- 未解项：Changelog 格式、产品启动/认证、时长公式、TTS 供应商、审核标准。

## Round 4

- 观点：输入应由 CLI 文档地址驱动，而非假设所有产品将 Changelog 放在仓库根目录。
- 证据：用户确认 CLI 接收文档地址；StartUpOS 位于 `/Users/archersado/workspace/startupos`。只读探查显示其版本说明约定在 `docs/changes/releases/v<version>/changelog.md`，全量流水在 `docs/changes/changelog.md`。[S-004]
- 反例或冲突：允许任意本机路径会扩大非预期读取范围，因此需要 path allowlist 和秘密文件拒绝规则。
- 暂定结论：添加 Source Resolver；StartUpOS release changelog 是可推导默认值，显式 `--source` 仍优先。
- 未解项：StartUpOS 启动/认证、Markdown 解析细则、TTS 供应商、视频链接服务和审核标准。

## Round 5

- 观点：首发样本、运行目标、配音和审核传递方式均已确定，可以开始设计实际适配器。
- 证据：用户选择 StartUpOS 桌面版、`v0.3.3`、Edge TTS 和 HTTP 预览；已验证 v0.3.3 Changelog 文件存在，包含四组发布说明。[S-005]
- 反例或冲突：Changelog 中“验证”条目未必对应可录制 UI；它必须由场景规划器转为旁白或在人工审核时移除，不能虚构演示。
- 暂定结论：首发构建 `desktop-runner`、`edge-tts`、`preview-server` 三个适配器；预览服务仅监听 loopback。
- 未解项：桌面启动协调、稳定的 UI 操作路径、TTS 故障降级和审核通过标准。

## Round 6

- 观点：产品入口发现是版本化演示的核心能力，必须建模为代码证据检索，而非静态录制脚本。
- 证据：用户要求根据 Changelog 与 commit 中的代码定位入口，并确认首条聚焦感知与 IM 路由、默认 `zh-CN-XiaoxiaoNeural`，且审核同时检查事实、录屏、音画和时长。[S-006]
- 反例或冲突：提交可能触及内部模块但没有直接 UI 入口；此类候选不能被自动化执行。
- 暂定结论：引入 Code Evidence Explorer，要求每个自动镜头附 Changelog+commit/diff 证据与置信度；低置信度内容降级处理。
- 未解项：commit 与 feature 的匹配算法、置信度阈值、StartUpOS 具体可录制 UI 流程、TTS 降级。

# 方案

- 评价标准：能改变 MVP 边界、风险控制或适配器优先级。
- 备选方案：一次性收集完整 PRD；或分轮提问。
- 选定方案：首发采用“CLI 文档地址 → Changelog + commit 代码证据 → StartUpOS Desktop 自动演示 → Xiaoxiao TTS/字幕 → 动态时长渲染 → loopback HTTP 预览 → 人工审核”的链路；`v0.3.3` 感知与 IM 路由是首个验收样本。
- 否决理由：完整问卷在项目前提不足时会制造低质量假设。
- 行动与验证计划：以 v0.3.3 感知与 IM Changelog、关联 commit/diff、StartUpOS Desktop、Xiaoxiao 音轨和 loopback 预览审核流程验证实现条件。

# 架构更新

- 计划修改：增加 code-evidence explorer、证据置信度门禁、desktop-runner、Xiaoxiao TTS adapter、loopback preview server 与 v0.3.3 感知/IM 验收样本。
- 实际修改：已更新业务、产品、技术三维架构及 `traceability.md`。
- 未更新及原因：commit 关联算法、具体 UI 流程、TTS 故障降级和审核阈值留待实现前的最后一轮确认。

# 验证与关闭

- 验证结果：架构映射已完成；实现验证 pending。
- 遗留风险：没有 StartUpOS 的本地启动、稳定 UI 流程、测试数据和认证方案前，自动录屏只能保持为可替换适配器。
- 模式候选：无。
